## What is done

**Application shell and navigation**
- Two destinations, Library and Settings, with a console-style header; fullscreen on launch; F11 and Windowed/Maximized/Fullscreen modes; Game Details as a full-window overlay.
- Full controller, keyboard and mouse navigation, with an adaptive hint bar whose button symbols follow the connected controller's layout and its mapping profile. Button chips are one component (`InputKeyChip.qml`); PlayStation face buttons are drawn as shapes so they sit centred (2026-11-25).
- System menu (Start/Esc): Resume, Settings, Quit, about 15% larger for a TV, with a Move / Select / Resume hint row. Opening it plays the pause sound ("settle", `assets/sounds/pause.wav`); choosing Settings closes it silently.
- Interface scale (Auto from the screen's logical height, or 75–200%) applied at startup through `QT_SCALE_FACTOR`; changing it restarts the app on the same Settings page.

**Library**
- Twelve library systems, ordered by maker and generation: Game Boy, Game Boy Color, Game Boy Advance, SNES, N64, GameCube, Wii, Wii U, PS1, PS2, Xbox, Xbox 360; each has its folder, file types, detection when adding games, metadata mappings and box shape.
- Four views: Shelves (with a spotlight panel), Grid (sectioned by platform in All Platforms), List with a preview pane, and a full-screen hero Carousel. Covers use their platform's box shape (`GameArtwork.qml`). A system picker in the header (one chip; LB/RB and Q/E step through systems with games, the list groups them by maker), expanding search, per-view size presets, all persisted.
- Backgrounds: theme gradient, live GPU shader waves (color, motion, quality; paused during games and under Reduced motion), or the user's own image (Fill/Fit, Dim).
  - [x] Retro patterns for the Still background (2026-11-27, branch `feature/retro-backgrounds`; design option B approved on the "RecompStation retro backgrounds" canvas): the Gradient tile is now **Still**, and while it's chosen a Pattern row offers Gradient, CRT glow (the default for new installs), Dithered sunset and Circuit board. Drawn by `shaders/retro.frag` through `RetroBackground.qml` into a cached layer, so a pattern is redrawn only when the window size, theme or pattern changes, never while browsing; sizes are in logical pixels so they look the same on every screen. CRT glow, the starfield and the circuit board take the theme's colors and accent; the sunset keeps its own warm palette. The software renderer (no shaders) shows the gradient. The choice is kept with the other background settings (`LibraryVisuals/stillPattern`). To check: each pattern in every theme, the tile and live preview, controller focus in the Pattern row, and redraws when the window is resized. First test 2026-11-27: Circuit board fine. CRT glow drew a smaller tube inside the window, which looked like a frame around nothing: now the whole window is the screen (glow in the middle, corners darkening like curved glass, softer scanlines, a faint phosphor stripe). Dithered sunset was too bright and its sun too big behind the covers: now dusk colors, darker hills and a smaller, dimmer sun low on the horizon. Pixel starfield not tried yet. Second look 2026-11-27: the new CRT glow and sunset approved. CRT glow is the default for new installs only (set when first-time setup opens, so copies already set up keep the gradient until their owner picks a pattern). Pixel starfield taken out of Still (2026-11-27): a twinkling starfield replaces it as an animated background; a saved "stars" shows the gradient. Its shader code stays in `retro.frag` for that.
  - [x] Moving background scenes (2026-11-27, same branch; option 1 on the design canvas, at most four scenes like Still): the Waves tile is now **Moving**, and while it's chosen a Scene row offers Waves (the default), Twinkling stars, Floating lights and Color flow. `WaveBackground.qml` picks the shader by scene (`waves.frag`, `stars.frag`, `lights.frag`, `flow.frag`), so all four share the Color, Custom hue, Motion and Quality settings, the frame-rate limit and the pausing (games, Reduced motion, inactive window); each scene words its Color and Motion lines its own way. Twinkling stars replaces the still Pixel starfield (four-step twinkle, a shooting star every so often); Floating lights follows the user's reference picture (lights gathered at the bottom over a glow, smaller after review); Color flow blends the chosen color with two neighbours on the color wheel. Kept in `LibraryVisuals/movingScene`. To check: each scene in the Library, the tile and Scene-row previews, every color (Theme and Custom too), Motion and Quality on each, and Low quality on built-in graphics. Approved by the user 2026-11-27 ("It's beautiful") and merged into `ui/interface-redesign`.
- Filesystem monitoring and automatic reconciliation of added and removed games.

**Game Details**
- Hero layout (screenshot backdrop, cover at its true shape, chips, title), one primary action that follows the launcher lifecycle (Install → Downloading → Play), Check for updates, Uninstall under ⋯, About, selectable screenshots with a full-screen viewer, and a Recompilation card. LB/RB switch games.

**Settings** (category rail with live summaries, ◀ value ▶ rows, toggles, preview pane)
- Appearance (four themes: Electric Blue, Midnight Violet, Aurora, Carbon; Ember retired), Display, Background, Library (including Add games), Metadata, Controller (layout drawing, live button test, symbols, remapping), Application (about, storage use, data and log folders, launchers whose game is gone, reset settings).
- Written for players: each description says what the setting does and what it keeps, without internals; status lines read as short sentences (2026-11-25).
- Application › Updates: RecompStation checks GitHub for new versions (daily at startup, or Check now), asks before updating, and updates the AppImage or portable zip in place; source builds link to the website (see roadmap 9).

**Metadata**
- LaunchBox (offline catalog, first by default, indexed for supported platforms only) and TheGamesDB (key entered in the app and stored in an owner-only file; the environment variable still wins).
- Automatic matching after every scan, including games added while the app runs; TheGamesDB failures fall back to LaunchBox and are retried an hour later; enabling LaunchBox or updating its catalog re-matches unmatched games. Covers and screenshots from either provider.

**First-time setup and adding games**
- Full-window setup: library folder (just the folder choice; suggests `~/Games/RecompStation` or `~/RecompStation`), Add games, covers and info (LaunchBox progress with stages, Cancel and Retry), ready.
- `GameImporter`: finds games in folders or dropped files, identifies the system (extension plus disc headers), keeps `.cue` tracks together, unpacks cartridge ROMs (N64, GB, GBC, GBA, SNES) from `.zip`/`.7z`, copies (default) or moves them into the platform folders, never overwrites. Available from setup, Settings › Library and drag-and-drop.

**Launchers**
- Lifecycle: downloads checked against the SHA-256 GitHub publishes; installed versions recorded and shown; "Update to <version>" swaps versions safely, keeps the player's files and rolls back on failure; interrupted updates finished or undone at startup; leftover downloads cleared at startup (see roadmap 3).
- Curated catalog of 42 projects (30 N64, 4 GameCube, 2 each for PS1, Xbox, Xbox 360 and SNES) queried through the GitHub API; Linux x86_64/arm64 AppImage, ZIP and TAR.GZ assets (including a ZIP wrapping a TAR.GZ); projects that publish only pre-releases (`includePrereleases`, with an automatic fallback when there is no full release); staged download, extraction, install, launch, uninstall, rediscovery. Game input ownership while a launcher runs. The launcher file inside an archive is matched by name without case (it must still be the only match).

**Seamless play** (`LaunchPreparer`, `RomInspector`, the `launch` recipe in `data/projects.json`)
- How Play hands over the game (user's rule, 2026-11-26), for every launcher:
  - A cartridge ROM, and the launcher has its own settings screen: the ROM is attached (selected) and the launcher opens; the player starts the game there (`selectfile`, `--launcher --rom`, or a placed ROM for N64Recomp/HarbourMasters launchers).
  - A cartridge ROM, and the launcher has no settings of its own: the game starts straight away (`fileargument`).
  - A disc image (GameCube, Wii), and the launcher has settings: the disc is attached, not started (`selectfile`).
  - A disc image, and the launcher has no settings: the disc starts straight away (`discargument`).
  - A launcher that already finds and starts the game by itself (BlueWake): left alone (`manual`).
  - A launcher that builds the game from your copy first: the game is attached so the build starts by itself.
- Play hands the library's game file to the launcher, so it opens straight to the game. Catalog-driven methods, no per-project code:
  - `n64recomp` (22 projects): the ROM is checked against the launcher's own XXH3-64 checksum (read from each project's source, `.rom_hash`) and copied, padded and converted to big-endian, to `~/.config/<program_id>/<game_id>.z64` — where N64ModernRuntime keeps it after its first start. A `portable.txt` in the install folder means the install folder instead.
  - `harbourmasters` (Shipwright, Ghostship, PaperBoat): `SHIP_HOME` is set to `~/.local/share/<name>`, so saves live outside the managed install folder (Ghostship and PaperBoat previously saved into it, because libultraship falls back to the working directory). Existing saves and settings are copied there once; the ROM is placed there for the port's own extraction prompt.
  - `romfolder` (Pokémon Snap, Snowboard Kids): the ROM goes into the launcher's data folder, with saves kept beside it.
  - `discargument` (Luigi's Mansion: `--disc <file>`) and `fileargument` (Super Metroid, Mega Man X: `--launcher --rom <file>`, so their own launcher opens with the ROM selected): the game file itself is passed as an argument.
  - `selectfile` (Super Mario World, DKC2, DKC3, Paper Cut, melee-pc; added 2026-11-26): the game file is written into the launcher's own settings file, so its launcher opens with the game chosen but not started (the player presses its Play). Catalog entries name only the file, its format (`whole`, `firstline`, `listline`, `quotedkey` with a key) and its folder: the launcher's own (`rom.cfg` beside the program, or beside the AppImage), or SDL's folder for an app name (`~/.local/share/<app>`, `%APPDATA%\<app>`), a portable copy's subfolder when its marker file is beside the program (not for AppImages), or a folder variable the player set (Paper Cut's `TTYD_USER_DIR`). Other lines in those files are kept. Read from each project's source: SMW reads `rom.cfg` for its launcher and ignores `--rom` there (so `--launcher --rom` opened it with no ROM); DKC2/3 read `rom.cfg` with `--launcher`; Paper Cut lists `library.txt` and selects `last_disc.txt`; melee-pc reads `disc "<path>"` from `launcher.cfg` (a disc argument would start the game).
  - More `selectfile` formats and folders (2026-11-27): `inikey` (a `key=value` line written as it is, in an optional `[section]`; Melee Unlocked's `iso=`, Recharged's `[game] disc=`, MZM's `rom=`, Stunt Race FX - DECOMP's `rom=`) and `jsonkey` (a top-level key of a JSON object, other keys kept; a file with comments is left alone: Nookery's `backend.discPath`, Pikmin Recomp's `iso`, RE:UC Recomp's `game`). A user folder can be `~/.config/<app>` (`"linuxBase": "config"`), and `%LOCALAPPDATA%\<app>` or the launcher's own folder on Windows (`"windowsBase": "local"` or `"launcher"`). Keys may hold dots and capitals.
  - `gameVariable` (2026-11-27) on `fileargument`/`discargument`: the game's path goes into a variable the launcher reads (Star Fox Enhanced's `STARFOX_RETAIL_ROM`, SwitchWaker's `COS_DISC`), with or without arguments. The same name rules as `environment` (no `PATH`, `LD_*`, `XDG_*`, `QT_*`, `SDL_*`, `WINE*`).
  - `placefile` (2026-11-27): the game file is put where the launcher looks for it, under the name it looks for (`"file"`: fixed, `{name}` for its own name, `GMPE01_00.{ext}`, in up to one subfolder like `roms/{name}`), in the same folders as `selectfile`. A hard link where the file system allows one (so a disc image isn't stored twice), else a copy; a file of the same size already there is kept, another one under that name is replaced. `windowsArguments` replace `arguments` for a Windows build ({placedPath}). For launchers that build or start from a file they find themselves: EarthBound Native, trio, alttp-dx (`zelda3.sfc` in its data folder), fe8-pc-port, partyboard, Eternal Darkness Recomp, darkuni's Umbrella Chronicles.
  - Arguments may also hold a number or a file in the launcher's folder (`generated/main.dol`), never `..` or an absolute path.
  - Through Wine, `selectfile` and file arguments now get the game as a `Z:\` path (Wine's whole-filesystem drive); before, Windows launchers with file arguments got nothing through Wine.
  - DKC1 has no launcher screen (it plays the ROM it gets, or the one it remembers, or asks with a file picker), so it uses `fileargument` and starts straight away.
  - `manual` (the other GameCube ports, Diddy Kong Racing, Glover-R, and the PS1, Xbox and Xbox 360 projects): the game page offers Show file and Copy path.
- Never replaces a file a launcher already has; library files are only read; the status line under Play explains wrong versions (region and revision from the ROM header) and wrong games.
- Display: launchers must write their own `graphics.json` (a file missing options crashes RecompFrontend launchers: `ds_option` is parsed as a number). RecompStation only changes `wm_option` in an existing file — "Start games in fullscreen" once per launcher (remembered in `launch/fullscreenApplied/<id>`), or the per-game Window choice every start. Widescreen ("Expand") is already the launchers' default.
- Settings › Library › Playing (prepare games, start in fullscreen); Game Details status line and Launch section (game file, window, saves folder); a short starting screen listing what was done.
- xxHash 0.8.5 header in `third_party/xxhash` (BSD 2-Clause).

## Roadmap

Ordered by priority. Each item ships on its own branch with tests, a build, and user validation.

### 5b. Runtime log — done
`runtime.log` is written for whoever reads a bug report: a session header (version and commit, system, desktop and session type, display, settings, library counts, installed launchers, data and log paths) and footer, one line per event (`2026-11-23 15:14:02.239 INFO  launch    …`), the home folder written as `~`, and the renderer (graphics API and OpenGL driver) once the window is up. Per-frame and per-request chatter (geometry, screenshot rotation, every metadata query) is debug-only; debug is off unless Settings › Application › Detailed logging is on or `RECOMPSTATION_DEBUG=1` (`QT_LOGGING_RULES` still overrides). Launcher output is captured to `logs/launchers/<project>.log` and, when a launcher crashes or exits with an error, its last 40 lines are copied into `runtime.log`.

## Key decisions

- Decisions about library candidates (approve, skip, which launcher, notes) live only in the Candidates spreadsheet; this document records what was added to the catalog and why, not the decisions themselves (2026-11-28).
- Controller-first, library-first, and fullscreen by default; RecompStation keeps its own visual identity (RecompLauncher, GPL-3, was used only as a reference).
- Artwork comes from LaunchBox and TheGamesDB box art; no other artwork provider is planned.
- TheGamesDB keys are supplied by each user; the app never ships one (TheGamesDB counts allowances per key and advised against bundling, 2026-11-24).
- Metadata is matched only when one result clearly fits; ambiguous games stay unmatched rather than getting the wrong cover.
- RecompStation never supplies game files and never overwrites or deletes the user's games; uninstalling a launcher keeps ROMs and saves. One exception, at the user's request: a .zip/.7z in a cartridge system's folder whose only file is a ROM is removed after that ROM has been unpacked next to it and its size checked; archives with other files are kept.
- RecompStation never creates a launcher's settings files; it changes single documented keys in files the launcher wrote itself.
- Launchers come from native Linux release assets of curated projects. Flatpak-only projects are an open question (Catalog, platforms and file formats), not ruled out: players shouldn't need to install Flatpak themselves.
- No settings without real behaviour: placeholder controls are removed until their feature exists.
- Settings text is written for players, not developers: say what a setting does and what it keeps, without internals such as file layouts, environment variables or render percentages (2026-11-25).
- Dependency removal never guesses: only packages the installer added are candidates, anything the system or other programs use (including optional dependencies, and `qt6-wayland` on Wayland) is kept, and nothing happens if the package manager's simulation would touch anything else (2026-11-25).
- Launchers match the system RecompStation is running on, detected at startup; on Linux the Linux build is preferred, and Windows builds run through the system's own Wine only when the player turns on the Linux-only Wine switch in Settings (greyed out without Wine), and then only by choice or when no Linux build exists. RecompStation never bundles or manages Wine (2026-11-25).
- Releases: an AppImage and a portable zip for 64-bit Linux (x86_64), Qt included, built by GitHub Actions; ARM later. Windows `.exe` builds follow once the Linux files work well (2026-11-24).
- Launcher updates replace the installed version only after the new one is unpacked and checked, keep the player's files, and roll back on failure; downloads are checked against the SHA-256 the project publishes on GitHub (2026-11-24).

## Build and development workflow

Dependencies:
- Qt 6.5 or newer, including Qt SVG and Qt Shader Tools (`qt6-shadertools` on Arch Linux, `qt6-shadertools-dev` on Debian); Debian 12 and Ubuntu 24.04 are too old
- A C++20 compiler and CMake; Ninja is recommended
- Optional, for faster builds: ccache and mold (or lld), picked up automatically
- libarchive (`libarchive` on Arch Linux, `libarchive-dev` on Debian)
- SDL2 for controller support (optional at build time)

From the repository root:

```bash
./scripts/setup.sh                  # new computer: dependencies, build, tests
./scripts/install_dependencies.sh   # dependencies only (Arch, or Debian 13+ / Ubuntu 25.04+)
./scripts/uninstall_dependencies.sh # remove what the installer added (--dry-run to preview)
./scripts/build.sh                  # Debug build
./scripts/build.sh --test           # build and run the CTest suites in parallel
./scripts/run.sh                    # start the app
```

`install_dependencies.sh` records the packages it adds (those not already installed, plus what they pulled in) in `~/.local/state/recompstation-dev/installed-packages`. `uninstall_dependencies.sh` removes only those, keeps any that something outside the list still needs (on Arch also as an optional dependency; `qt6-wayland` always on a Wayland desktop; on Debian, Essential, Required and Important packages), and stops if the package manager's own simulated removal would take anything else. Without the record it rebuilds it from apt's history (`/var/log/apt/history.log*`) or `/var/log/pacman.log`, using only installs whose command line was the installer's (Debian: qt6-shadertools-dev with libsdl2-dev; Arch: `pacman -S --needed` with cmake, qt6-base and qt6-declarative, which every version of the script used); with no such install found it removes nothing.

Choose a configuration with `./scripts/build.sh Release` or `./scripts/build.sh RelWithDebInfo`. The build script reuses the configured generator and build directory; keep the build directory and prefer incremental builds. Every new `.qml` or `.js` file must be listed in `QML_FILES` in `CMakeLists.txt` (the QML tests read from the source tree and will not catch a missing entry).

The CMake `WrapVulkanHeaders` warning is harmless. On Debian and openSUSE, configuring also prints many "The qml plugin '…' is a dependency of 'RecompStationApp', but the link target it defines … does not exist" warnings: those distributions leave out the CMake files for Qt's QML plugins, which only matter for static Qt builds. The plugins load at run time as usual, so these are harmless too (seen on Debian 13, 2026-11-25).

## Development principles

1. Keep `main` stable; develop on the redesign branch and short feature branches.
2. Keep the application buildable and runnable after each focused change.
3. Application logic in C++, presentation and navigation in QML; small reusable components over one large file.
4. Automate backend chores (scanning, matching, artwork) rather than exposing them as tasks.
5. Add tests whenever backend behaviour changes; run the full suite before merging.
6. Never delete the user's build directory, application data, games or saves during routine work.
